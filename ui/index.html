The idea

      
A classic MLFQ moves processes between queues based on CPU usage. In a trading system under attack that does not help:
        bot requests are short, so a classic MLFQ treats them as the most interactive jobs of all. Cyber-Adaptive MLFQ moves processes
        based on the behaviour of their source (IP or API token) instead.

      

        
Q0 · Verified human
Round Robin with a micro-quantum ( ticks). Highest priority.

        
Q1 · Suspicious
Non-preemptive Shortest-Job-First. Runs only when Q0 is empty.

        
Q2 · Quarantine
FCFS by arrival. Runs only when Q0 and Q1 are both empty.

      

      
Threat score (re-computed every tick for every live process)

      
score = ·velocity + ·frequency + ·anomaly

      
velocity = requests from the source in the last  ticks (sliding window, a std::deque), normalised by a cap of  req/tick.

         frequency = lifetime requests from the source, normalised by .

         anomaly = mean payload anomaly (0–1) in the window. Catches failed-login patterns in credential stuffing.

      
score ≥  → MALICIOUS → Q2 immediately; a running process is forcibly preempted.

         score ≥  → SUSPICIOUS → Q1 after its current quantum.

         otherwise → CLEAN → Q0.

      
Feedback rules

      
Aging / promotion: a source that stays calm for  ticks moves up one level. A source that was ever malicious can only climb back to Q, so a bot's queued backlog never floods the fast lane.

         Anti-starvation: a process waiting  ticks in Q2 is boosted to Q1 (on/off in Settings).

         CPU usage never demotes a process here. That is the key difference from the classic MLFQ.

      
What runs where

      
The whole simulation is the C++17 program ./cmlfq: a deterministic discrete-clock engine with four pluggable schedulers and real
        producer/consumer threads for ingestion. This page is only a viewer. Each button runs the binary with --json and draws the result.
        The exact command and its terminal output are in the Terminal output tab.
